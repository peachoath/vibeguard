## 1. 한 줄 요약

**"코드를 고치는 도구"에서 "라이브러리를 안전하게 올려주는 도구"로 좁힌다.**
대신 **"올려도 안 깨진다"를 테스트로 증명**하는 부분은 반드시 남긴다.

---

## 2. 용어 — 먼저 이것만 알면 된다

요즘 프로그램은 전부 직접 만들지 않는다. 남이 만든 부품(라이브러리)을 가져다 쓴다.

| 줄임말 | 우리말 | 검사 대상 | 난이도 |
|---|---|---|---|
| **SCA** | 라이브러리 검사 | 남이 만든 부품 | **쉬움** — 버전 번호만 대조 |
| **SAST** | 코드 검사 | 내가 짠 코드 | 어려움 — 코드를 이해해야 함 |

고치는 난이도도 다르다.

| | SCA (라이브러리) | SAST (코드) |
|---|---|---|
| 고치는 법 | `flask==2.0.1` → `flask==2.3.2` | 코드를 다시 작성 |
| 난이도 | **한 줄 수정** | 어려움. 잘못 고치면 프로그램이 망가짐 |

**이번 전환의 핵심은 SAST를 빼고 SCA에 집중하는 것이다.**

그 밖의 용어:

- **회귀 테스트** — 리포에 **원래부터 있던** 테스트들. "고치기 전에 잘 되던 게 여전히 잘 되나" 확인용.
- **샌드박스** — 남의 코드를 가둬놓고 실행하는 일회용 도커 컨테이너.
- **마운트** — 호스트의 폴더를 컨테이너가 들여다볼 수 있게 **창문을 내주는 것**. 복사가 아니다. 파일은 계속 호스트에 있다.
- **매니페스트** — 어떤 라이브러리를 쓰는지 적어 둔 파일. Python은 `requirements.txt`, `pyproject.toml` 등.
- **lock 파일** — 딸려 들어오는 것까지 포함해 **모든 버전을 정확히 못박아 둔 파일**. `poetry.lock`, `uv.lock` 등.

## 3. 왜 바꾸는가

### 3.1 원래 계획에서 가장 어려운 두 가지

| 원래 계획의 요소 | 왜 어려운가 |
|---|---|
| Claude가 **재현 테스트를 새로 작성** | 코드를 이해해서 공격 테스트를 짜야 한다. 성공을 보장할 수 없다 |
| Claude가 **취약한 코드를 리팩토링** | SQL 인젝션을 파라미터 바인딩으로 고치려면 진짜 코드 이해가 필요하다 |

이 둘이 4주차(W4)에 몰려 있었고, PRD가 스스로 "성패를 가르는 주"라고 적어 둔 구간이다.
**둘 다 SAST 때문에 필요한 것이고, SCA만 하면 둘 다 필요 없다.**

### 3.2 그런데 빼면 안 되는 것

샌드박스 실행까지 빼면 **Dependabot과 같아진다.** PRD §1.2의 비교표가 그대로 무너진다.

그리고 PRD가 정의한 사용자가 실제로 겪는 문제는 이것이다.

> "Snyk 경고 47건이 쌓여 있지만... **버전 올리면 뭐가 깨질지 몰라 방치**"

**방법을 몰라서가 아니라 무서워서 안 한다.** 그 두려움을 없애는 것이 회귀 테스트이므로,
이것만은 반드시 남긴다.

## 4. 확정 사항

| # | 결정 | 비고 |
|---|---|---|
| **D1** | **주력은 SCA(라이브러리 검사)** | SAST(코드 검사)는 추후 확장으로 미룬다 |
| **D2** | **재현 테스트 자동 생성은 하지 않는다** | 리포에 원래 있던 테스트를 쓴다 |
| **D3** | **패치는 매니페스트 버전 문자열 수정만** | 코드 리팩토링을 하지 않는다 |
| **D4** | **회귀 검증은 유지한다** | 패치 전후로 기존 테스트를 각 1회 실행. 이것이 유일한 차별점이다 |
| **D5** | **탐지는 다국어, 회귀 증명은 Python 우선** | §4.3 |
| **D6** | **컨테이너는 3종이며, 네트워크는 테스트 컨테이너에서만 차단한다** | §5.2. 스캔·설치 컨테이너는 네트워크를 연다 |
| **D7** | **Trivy DB는 호스트에서 마운트한다 — 이유는 보안이 아니라 속도** | §6.2. 실무에서도 표준적으로 하는 처리 |
| **D8** | **의존성 설치 단계를 파이프라인에 포함한다** | §5.1. 기존 계획에 아예 빠져 있던 단계 |
| **D9** | **lock 파일이 없는 리포만 완전 지원한다** | §4.4 |
| **D10** | **샌드박스 러너는 Python으로 유지** | TypeScript로 포팅하지 않는다 |
| **D11** | **패치 재시도 상한은 2회** | PRD §6.4를 따른다 |

### 4.1 무엇을 증명한다고 말할 수 있는가 (중요)

원래 계획의 "FAIL→PASS 증명"은 없어진다. 대신 세 가지를 각각 다른 근거로 주장한다.
**이 구분을 흐리면 안 된다.**

| 주장 | 근거 | 증명 방식 |
|---|---|---|
| "취약하다" | NVD·OSV·GHSA 공식 기록 | **문서 근거** (테스트로 증명하지 않음) |
| "고쳤다" | 매니페스트 버전이 안전 버전 이상 | **버전 대조** |
| **"안 깨졌다"** | 기존 테스트가 패치 전후 모두 통과 | **테스트 실행 증명** ← 우리의 차별점 |

즉 **"취약함을 테스트로 증명한다"고 말해서는 안 된다.** 우리가 테스트로 증명하는 것은
"하위 호환이 유지된다"이다.

### 4.2 왜 Python인가 (근거가 바뀌었음)

| | 원래 (SAST 포함) | **지금 (SCA 중심)** |
|---|---|---|
| 왜 하나로 좁히나 | Claude가 **재현 테스트를 작성**해야 하는데, 러너가 여러 개면 증명 신뢰도가 떨어져서 | **의존성 설치와 테스트 실행 방식이 언어마다 다른데, Python이 가장 단순해서** |

언어별 의존성 설치 난이도:

| 언어 | 설치 방법 | 난이도 |
|---|---|---|
| **Python** | `pip install -r requirements.txt` | **가장 단순** |
| Node | `npm ci` (lock 필수, `node_modules`가 거대) | 중간 |
| Java | Gradle/Maven — **빌드까지** 필요 | 무거움 |
| Go | `go mod download` + 컴파일 | 무거움 |

### 4.3 언어 지원 등급

**탐지는 언어를 거의 가리지 않는다.** Trivy가 매니페스트 파일을 읽기만 하므로 언어가 늘어도
우리 부담이 없다. **회귀 검증은 다르다.** 언어마다 설치와 테스트 실행 방법이 다르다.

| 등급 | 대상 | 산출물 |
|---|---|---|
| **기본** | 모든 언어 | 탐지 + 버전 상향 PR (**증명 없음**) |
| **검증** | 테스트가 있는 **Python** 리포 | + **회귀 통과 증명** ← 시연 대상 |

이 등급 구분은 BusinessModel 문서의 FREE / PRO 구분과 그대로 대응한다.

### 4.4 lock 파일 정책

lock 파일이 있는 리포도 **받는다. 탐지는 오히려 더 정확하다** — Trivy가 딸려 들어온
라이브러리까지 전부 검사하기 때문이다. 문제는 패치 단계다.

lock 파일이 있으면 매니페스트의 버전만 고쳐도 설치에 반영되지 않는다. lock 파일도 재생성해야
하고, 그러려면 패키지 관리 도구를 실행해야 하며, 도구마다(poetry / uv / pipenv / pip-tools)
방법이 다르다.

| 리포 형태 | 탐지 | 패치 | MVP 지원 |
|---|---|---|---|
| `requirements.txt`만 | ✅ | ✅ 한 줄 수정 | **완전 지원** |
| `pyproject.toml`만 (lock 없음) | ✅ | ✅ 한 줄 수정 | **완전 지원** |
| `poetry.lock` / `uv.lock` 있음 | ✅ 더 정확 | ⚠️ lock 재생성 필요 | **탐지만.** "수동 확인 필요" 안내 |

이는 PRD의 **정직성 원칙**("안 되는 건 안 된다고 말한다")을 그대로 적용한 것이다.

> **참고.** 주 사용자가 "Claude Code로 코드를 대량 생성하는 개발자"인데, AI가 만든 Python
> 프로젝트는 대개 `requirements.txt`를 쓴다. 즉 **가장 잘 지원하는 형태가 곧 타겟 사용자의
> 형태**다. 스코프를 줄이는 것이 아니라 타겟에 맞추는 것이다.

## 5. 새 파이프라인

### 5.1 전체 흐름

```
[호스트]  대상 리포 클론
             ↓
🐳 ① 스캔     네트워크 O, DB 마운트    Trivy → 취약 라이브러리 목록(JSON) → 소멸
             ↓
[호스트]  Claude + advisory-mcp 판단
          · 이 CVE가 이 리포에 실제로 해당되나 (오탐 걸러내기)
          · 어느 버전까지 올릴까 (보안 vs 호환성 저울질)   ← AI의 핵심 역할
             ↓
🐳 ② 설치     네트워크 O               pip install → /venv 에 저장 → 소멸
🐳 ③ 테스트   네트워크 X, /venv 마운트  pytest → 통과 확인 (= 원래는 멀쩡했다) → 소멸
             ↓
[호스트]  매니페스트 버전 문자열 수정 (한 줄)
             ↓
🐳 ② 설치     네트워크 O               바뀐 패키지만 업그레이드 (빠름) → 소멸
🐳 ③ 테스트   네트워크 X               pytest → 통과 확인 (= 안 깨졌다) ✅ → 소멸
             ↓
[호스트]  증거 첨부 PR 생성
```

> **②번 설치 단계는 기존 계획에 아예 없었다.** 없으면 회귀 테스트가 `ModuleNotFoundError`로
> 실패한다(§6.3에서 실증). 대상 리포의 라이브러리는 우리 이미지에 들어 있지 않기 때문이다.

### 5.2 컨테이너 3종과 네트워크 정책

**모든 컨테이너를 똑같이 조일 필요가 없다. 위험도가 다르기 때문이다.**

| | 하는 일 | 네트워크 | 남의 코드가 실행되나 | 위험도 |
|---|---|---|---|---|
| **① 스캔** | Trivy로 매니페스트 읽기 | ✅ **연다** | ❌ 안 함 | 낮음 |
| **② 설치** | `pip install` | ✅ **연다 (필수)** | ⚠️ 패키지 설치 스크립트 | 중간 |
| **③ 테스트** | `pytest` 실행 | ❌ **절대 금지** | ✅ **함** | **높음** |

> **지켜야 할 한 줄:**
> **남의 테스트 코드가 실행되는 컨테이너에는 네트워크가 없다.**
> 이것만 지키면 나머지는 실무처럼 편하게 가도 된다.

②번이 "중간"인 이유: 여기서 실행되는 것은 **PyPI 패키지의 설치 스크립트**이지 **대상 리포의
코드**가 아니다. 일반 개발자가 `pip install` 할 때 지는 위험과 같은 수준이다.
`--only-binary=:all:` 옵션을 주면 그마저도 대부분 차단된다(미리 빌드된 패키지만 쓰므로
`setup.py`가 실행되지 않는다).

②·③ 모두 네트워크를 제외한 나머지 격리(비특권 사용자, `--cap-drop=ALL`, 메모리·프로세스
상한, 읽기 전용)는 그대로 유지한다.

### 5.3 반드시 지킬 경계 규칙

- **컨테이너는 실행기이며 편집기가 아니다.** 패치와 git 작업은 전부 호스트에서 한다.
- **컨테이너끼리 통신하지 않는다.** 서로 다른 시각에 태어나고 죽으므로 만날 일이 없다.
  정보를 들고 있는 것은 호스트이고, 주고받기는 마운트된 폴더로만 이루어진다.
- **GitHub 토큰과 API 키는 어떤 경우에도 컨테이너에 들어가지 않는다.**
- **Claude는 컨테이너 안에서 실행되지 않는다.** 호스트가 컨테이너의 출력(글자)을 읽어
  Claude에게 전달한다.

### 5.4 컨테이너 실행 횟수

리포당 스캔 1회. 취약점 1건당 **설치 2회 + 테스트 2회**.
재현 테스트 생성이 없으므로 재시도 루프도 없다.

## 6. 실측으로 검증된 사실 (2026-09-10)

추측이 아니라 실제로 만들어 돌려본 결과다.

### 6.1 네트워크를 끊고도 Trivy 스캔이 된다

`--network none`, `--user 1000:1000`, `--cap-drop ALL`, `--read-only`를 **전부 건 상태**에서
스캔이 성공했다(종료 코드 0). 결과 JSON이 호스트에 정상 생성되었고, 필요한 필드가 모두 있었다.

```
패키지: pyyaml    현재 5.1     → 안전 5.2      CVE-2019-20477   CRITICAL
패키지: flask     현재 0.12.2  → 안전 0.12.3   CVE-2018-1000656 HIGH
패키지: jinja2    현재 2.10    → 안전 2.10.1   CVE-2019-10906   HIGH
(총 30건 탐지)
```

> **D6에 따라 실제로는 스캔 컨테이너의 네트워크를 열지만**, 위 실험은 "필요하면 완전 오프라인도
> 가능하다"는 안전망이 확보되어 있음을 뜻한다. 시연장 인터넷이 불안하면 이 구성으로 바꾸면 된다.

### 6.2 DB는 이미지에 굽지 말고 마운트한다 — 이유는 속도

두 방식을 모두 만들어 비교했다.

| | 이미지에 굽기 | **호스트에서 마운트 (채택)** |
|---|---|---|
| 이미지 크기 | 1.93GB | **442MB** |
| DB 갱신 | 이미지 재빌드 (약 10분) | **파일만 교체, 재빌드 불필요** |

**마운트의 주된 이유는 보안이 아니라 속도다.** 컨테이너는 `--rm`으로 뜨고 사라지므로 안에
받은 DB도 함께 사라진다. 마운트하지 않으면 **스캔할 때마다 112MB를 다시 받는다**(약 1분).
Trivy를 도커로 돌릴 때 캐시를 마운트하는 것은 **실무의 표준적인 처리**이며 우리만의 조치가
아니다.

읽기 전용(`:ro`) 마운트로도 정상 동작함을 확인했다.
측정값: DB 압축 112MB / 전개 후 1.3GB, 최초 다운로드 약 10분, 갱신 주기 1일.

### 6.3 대상 리포의 라이브러리는 이미지에 없다 (설치 단계 필요의 근거)

`flask`를 쓰는 리포의 테스트를 네트워크 없는 컨테이너에서 돌리면 이렇게 실패한다.

```
E   ModuleNotFoundError: No module named 'flask'
!!!! Interrupted: 1 error during collection !!!!
```

우리 이미지에는 pytest만 들어 있고 대상 리포의 라이브러리는 없다. **이것이 §5.1의 ②번
설치 단계가 필요한 이유다.**

### 6.4 구현 시 필요한 Trivy 옵션

D6대로 스캔 컨테이너의 네트워크를 열면 아래 대부분이 불필요해진다. 완전 오프라인으로
전환할 경우에만 필요하다.

| # | 증상 | 해결 | D6 적용 시 |
|---|---|---|---|
| 1 | DB 다운로드가 5분에서 잘림 | `--timeout 30m` | **여전히 필요** |
| 2 | 실행 시 DB를 업데이트하려 함 | `--skip-db-update --offline-scan` | 불필요 |
| 3 | 마운트한 DB를 찾지 못함 | `--cache-dir /opt/trivy-cache` 명시 | **여전히 필요** |
| 4 | 불필요한 검사까지 수행 | `--scanners vuln` | 권장 |

### 6.5 샌드박스 러너 자체는 검증 완료

기존 `runner.py`는 격리 설정을 요구사항(NFR-S1·S2)에 맞춘 뒤 재검증을 마쳤다.
검사 9종 전부 통과(20초), 적대적 리포의 공격 8종 전부 차단, 호스트 무결성 이상 없음.

### 6.6 성능 — 병목은 의존성 설치다

| 단계 | 소요 |
|---|---|
| 컨테이너 생성·폐기 | 0.36초 |
| pytest 실행 (3건) | 0.2초 |
| **라이브러리 설치** | **수십 초** ← 병목 |

컨테이너 오버헤드는 병목이 아니다. **pip 캐시를 마운트하면 두 번째 설치는 크게 빨라진다.**

## 7. 실무와 우리의 차이 (오해 방지)

**실무에서 Trivy는 `trivy fs .` 한 줄로 쓴다.** 격리도, 오프라인 옵션도 쓰지 않는다.
우리가 더 복잡한 이유는 Trivy 때문이 아니다.

| | 실무의 일반적 사용 | **우리** |
|---|---|---|
| 검사 대상 | 내 회사 코드 | **모르는 사람의 리포** |
| 코드를 실행하나 | ❌ 스캔만 | ✅ **테스트를 돌림** |
| 실행 환경 | CI 러너 (매번 새로 만들고 버림) | **서버 하나에서 반복** |

CI 러너는 이미 일회용이라 격리를 따로 할 이유가 없다. 우리는 서버에서 계속 돌리므로 격리를
직접 만들어야 한다. **그리고 그 격리가 정말로 필요한 곳은 ③ 테스트 컨테이너 하나뿐이다.**

## 8. AI가 판단하는 지점 (발표에서 반드시 짚을 것)

SAST를 빼면 "이거 AI가 왜 필요하냐, 스크립트로도 되지 않느냐"는 질문이 나온다.
답할 근거는 아래 네 가지이며, **실측에서 실제 사례를 확보했다.**

| # | AI가 판단하는 것 | 스크립트로 안 되는 이유 |
|---|---|---|
| 1 | 이 경고가 진짜인가 | 취약한 함수를 실제로 호출하는지 코드를 봐야 안다 |
| 2 | **어디까지 올릴까** | 보안과 호환성을 저울질하는 판단 |
| 3 | 깨졌다면 왜 깨졌나 | 테스트 실패 로그를 읽고 원인을 설명해야 한다 |
| 4 | PR 본문 작성 | 이 리포 맥락에 맞게 위험을 설명해야 한다 |

**2번의 실제 사례** (6.1 실측에서 나온 `urllib3`):

```
현재 1.24.1
  CVE-2019-11324 → 1.24.2 부터 안전
  CVE-2020-26137 → 1.25.9
  CVE-2023-45803 → 1.26.18
  CVE-2024-37891 → 2.2.2
  CVE-2026-44431 → 2.7.0
```

1.24.2로 올리면 한 건만 해결된다. 전부 해결하려면 2.7.0이 필요한데 이는 1.x → 2.x
**메이저 점프**라 깨질 위험이 크다. **Trivy는 목록만 주고 어디까지 올릴지는 정해주지 않는다.**
이 판단이 Agent 2와 `advisory-mcp`의 존재 이유다.

## 전환의 핵심 (이것만은 정확히 이해하고 시작할 것)

1. SAST(코드 정적 분석)를 MVP에서 제외하고, SCA(라이브러리 취약점 검사)에 집중한다.
2. "Claude가 재현 테스트를 새로 작성해서 FAIL→PASS를 증명한다"는 흐름을 **삭제**한다.
3. 대신 "리포에 원래 있던 테스트를 패치 전후로 각 1회 실행해서 **하위 호환이 깨지지
   않았음**을 증명한다"로 대체한다.
4. 패치는 매니페스트의 버전 문자열 수정만 한다. 코드 리팩토링을 하지 않는다.
5. 탐지는 다국어를 지원하고, 회귀 증명은 Python(pytest)을 우선한다.
6. **파이프라인에 "의존성 설치" 단계를 새로 추가한다.** 기존 PRD에는 이 단계가 없는데,
   없으면 회귀 테스트가 ModuleNotFoundError로 실패한다.
7. **컨테이너는 3종이며 네트워크 정책이 서로 다르다.** 아래를 정확히 반영할 것.

## 컨테이너 3종과 네트워크 정책 (새로 추가되는 개념)

| | 하는 일 | 네트워크 | 남의 코드 실행 | 위험도 |
|---|---|---|---|---|
| ① 스캔 | Trivy로 매니페스트 읽기 | 연다 | 안 함 | 낮음 |
| ② 설치 | pip install | 연다 (필수) | 패키지 설치 스크립트 | 중간 |
| ③ 테스트 | pytest 실행 | **절대 금지** | 함 | 높음 |

핵심 원칙: **남의 테스트 코드가 실행되는 컨테이너에는 네트워크가 없다.**

②·③ 모두 네트워크를 제외한 나머지 격리(비특권 사용자, --cap-drop=ALL, 메모리·프로세스
상한, 읽기 전용)는 유지합니다. ②에는 --only-binary=:all: 을 적용해 설치 중 임의 코드
실행을 차단합니다.

기존 NFR-S1은 "스캐너·테스트 실행은 전부 --network=none"으로 되어 있는데, 이를
**컨테이너 역할별로 네트워크 정책을 구분하는 형태로 개정**해 주세요. 격리 자체를 완화하는
것이 아니라, 위험도에 맞게 차등 적용하는 것입니다.

## 특히 주의할 것 — 증명의 의미가 바뀐다

전환 후에는 세 가지 주장을 서로 다른 근거로 뒷받침합니다. 이 구분을 흐리지 마세요.

- "취약하다"  → NVD/OSV/GHSA 공식 기록 (문서 근거. 테스트로 증명하지 않음)
- "고쳤다"    → 매니페스트 버전이 안전 버전 이상 (버전 대조)
- "안 깨졌다" → 기존 테스트가 패치 전후 모두 통과 (테스트 실행 증명) ← 유일한 차별점

**"취약함을 테스트로 증명한다"는 표현을 쓰면 안 됩니다.** 우리가 테스트로 증명하는 것은
하위 호환 유지입니다.

## 절대 바꾸지 말 것

- VibeGuard 자체의 기술 스택 (Spring Boot 4 / Java 21 / React 19 / Node 22 / Supabase).
  이번 전환은 "검사 대상 리포"의 이야기이지 우리 스택의 이야기가 아닙니다.
- MCP 4종 구성. 하나도 제거되지 않습니다.
- 4개 에이전트 구조. 유지됩니다.
- main 직접 푸시 금지, 자동 머지 영구 비활성.
- 서브에이전트 대신 독립 세션을 쓰는 설계 결정(PRD §5.3).
- NFR-S3(토큰 암호화), S4(HMAC), S6(프롬프트 인젝션 방어), S7(감사 로그), S8(클론 삭제).
