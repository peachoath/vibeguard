# VibeGuard 신뢰도 모델 (Trust Model)

> "AI가 올린 버전을 왜 믿을 수 있는가"를 정의하는 문서.
> VibeGuard의 신뢰도는 **검증 · 시스템 · 투명성 · 정직성** 4개 축에서 나온다.
> 대부분 [PRD](./VibeGuard_PRD.md)에 이미 설계되어 있으며, 이 문서는 그것을 "신뢰도" 관점으로 재배치한다.

| 항목 | 내용 |
|---|---|
| 문서 버전 | **v2.0 (방향 전환: SAST→SCA, 회귀 증명 중심)** |
| 최종 수정 | 2026-09-10 |
| 관련 문서 | [VibeGuard_PRD.md](./VibeGuard_PRD.md) · [VibeGuard_BusinessModel.md](./VibeGuard_BusinessModel.md) · [VibeGuard_방향전환.md](./VibeGuard_방향전환.md) |

---

## 0. 요약

VibeGuard의 신뢰도는 세 가지 질문에 답하는 데서 나온다.

1. **AI가 올린 버전을 믿을 수 있는가?** → 검증 신뢰
2. **우리 시스템 자체가 안전한가?** → 시스템 신뢰
3. **판단 근거를 투명하게 보여주는가?** → 투명성 신뢰

여기에 **"안 되는 건 안 된다고 말한다"**는 정직성 신뢰를 더한 4개 축이다.
심사에서 가장 임팩트가 큰 것은 단연 **검증 신뢰(하위 호환 회귀 증명)** 이다.

> **핵심 원칙(방향 전환으로 바뀐 부분).** 우리는 "취약함을 테스트로 증명한다"고 말하지 않는다.
> 세 주장을 서로 다른 근거로 뒷받침하며, 이 구분을 흐리면 안 된다.
> - "취약하다" → NVD·OSV·GHSA 공식 기록 (문서 근거)
> - "고쳤다" → 매니페스트 버전이 안전 버전 이상 (버전 대조)
> - **"안 깨졌다" → 기존 테스트가 패치 전후 모두 통과 (테스트 실행 증명) ← 우리의 차별점**

```
             VibeGuard Trust
                    │
   ┌────────┬───────┴───────┬─────────┐
   ↓        ↓               ↓         ↓
 검증      시스템          투명성      정직성
(회귀증명)(격리·최소권한) (감사·근거) (실패 노출)
```

## 1. 검증 신뢰 — "올렸다"가 아니라 "올려도 안 깨짐을 증명"

VibeGuard의 심장이자 최대 차별점. (PRD §1.3, §6.4) 세 주장을 각각 다른 근거로 뒷받침한다.

| 주장 | 요소 | 근거 |
|---|---|---|
| "취약하다" | NVD/OSV/GHSA 공식 기록 교차 검증 (문서 근거, 테스트로 증명하지 않음) | PRD §6.3 |
| "고쳤다" | 매니페스트 버전이 안전 버전 이상임을 대조 | PRD §6.4 |
| **"안 깨졌다"** | 리포의 기존 테스트가 패치 전후 모두 통과 (설치→테스트 2회) | **PRD §6.4** |
| Regression 게이트 | 패치 후 테스트가 깨지면 PR 생성 차단. 버전 후보 낮춰 최대 2회 재시도 | PRD §6.4, D11, G4 |
| 최소 안전 버전 결정 | major 점프를 피해 호환성과 보안을 저울질 (Trivy 목록만으로는 불가) | PRD §6.3 |
| 증거 첨부 PR | CVE 근거 + 버전 변경 + 패치 전후 통과 로그를 PR 본문에 첨부 → 사람이 눈으로 검증 | PRD §6.5 |

> 우리가 테스트로 증명하는 것은 "취약함"이 아니라 **"하위 호환이 유지된다"** 이다. 재현 테스트를 새로 만들지 않으므로 "패치 전 FAIL 확인"이라는 단계는 없다.

## 2. 시스템 신뢰 — "우리 도구 자체가 안전한가"

보안 도구가 보안이 허술하면 치명적. (PRD §11.1 NFR-S)

| 요소 | 설명 | 근거 |
|---|---|---|
| 샌드박스 역할별 격리 | 컨테이너 3종 차등 정책. **테스트 컨테이너(③)만 네트워크 차단**, 공통 격리(비특권·`--read-only`·`--cap-drop=ALL`·메모리/PID 상한)는 3종 모두 유지 | NFR-S1 |
| **적대적 자체 검증** | 공격 8종(크리덴셜 탈취, 외부 유출, 호스트 파일 열람, 리포 변조, 환경변수 탈취, 권한 상승, Docker 소켓 접근, tmpfs 고갈)을 실제로 시도해 전부 차단 확인 | **NFR-S9 (실측 증거)** |
| 실행 타임아웃 | 컨테이너 300초 초과 시 강제 종료·`TIMED_OUT` 처리 | NFR-S2 |
| 프롬프트 인젝션 방어 | 스캔 대상 리포의 README/주석을 **데이터로만** 취급 + 툴 화이트리스트 이중 방어 | NFR-S6 |
| 최소 권한 | GitHub App 권한을 `contents:write` + `pull_requests:write`로 한정. main 직접 푸시·자동 머지 영구 금지 | PRD §6.5 |
| deny-by-default 훅 | Claude Agent SDK `PreToolUse` 훅으로 리포 밖 파일 쓰기, `rm -rf`, 외부 네트워크 호출 차단 | NFR-S5 |
| 토큰 암호화 | GitHub 토큰 AES-256-GCM 저장, 로그·SSE·에러 응답에 노출 금지 (`TokenCipher` 구현됨). 토큰·키는 컨테이너에 들어가지 않음 | NFR-S3 |
| 콜백 무결성 | Runner ↔ Spring Boot 콜백 HMAC-SHA256 서명 검증 | NFR-S4 |
| 데이터 최소 보관 | 클론 리포는 스캔 종료 후 즉시 삭제, 소스 영구 저장 금지(스니펫만 보관) | NFR-S8 |

> **적대적 검증(NFR-S9)이 이 축의 유일한 실측 증거다.** "격리했다"는 주장을 실제 공격으로 검증한 것이 다른 도구와의 차이다. 네트워크를 완전히 끊고도 Trivy 스캔·pytest 실행이 정상 동작함도 함께 확인됐다.

## 3. 투명성 신뢰 — "왜 그렇게 판단했는지 보여준다"

블랙박스 AI는 신뢰받지 못한다. 판단 과정을 열어 보이는 것이 신뢰를 만든다.

| 요소 | 설명 | 근거 |
|---|---|---|
| 감사 로그 | 모든 에이전트 툴 호출을 `audit_logs`에 기록 → 사후 추적 가능 (검증 등급 차별 기능) | NFR-S7, §10 |
| 판단 근거(rationale) 노출 | Finding마다 CVE 정보·CVSS·안전 버전 결정 근거를 상세 탭에 표시 | F-06 |
| 실시간 진행 스트림(SSE) | 4개 에이전트가 무엇을 하는지 라이브로 노출 → "숨기지 않는다"는 인상 | F-04, §9.1 |
| Diff 뷰어 | 매니페스트 버전 변경(한 줄)을 직접 비교 | F-08 |
| 회귀 증거 뷰 | 패치 전 통과 로그 / 패치 후 통과 로그 / 버전 대조 3단 표시 | F-07 |
| 결과 원인 구분 | `test_runs.outcome`(PASSED/FAILED/NO_TESTS/OOM_KILLED/TIMED_OUT/INSTALL_FAILED)으로 "왜 증명이 안 됐는지"까지 노출 | §10 |

## 4. 정직성 신뢰 — "안 되는 건 안 된다고 말한다"

과장하지 않는 것도 신뢰의 일부. (PRD §4.2, §15)

| 상황 | 시스템 동작 | 근거 |
|---|---|---|
| 리포에 테스트가 없음 | 버전 상향은 하되 회귀 증명 없이 `NO_TESTS` 표기 — "증명 없음"을 숨기지 않음 | §4.2 |
| 의존성 설치 실패 (② 단계) | `INSTALL_FAILED`로 분류, 해당 Finding 패치 스킵, 로그 노출 | §4.2, R11 |
| lock 파일 존재 | 탐지만 하고 패치는 스킵, "lock 재생성 필요 — 수동 확인 필요" 안내 | §4.4 |
| 패치 후 회귀 테스트 깨짐 | PR 생성 차단(`REGRESSION_BLOCKED`), 깨진 테스트 목록과 함께 수동 검토 요청 | §4.2 |
| 재시도 상한 초과 | 버전 후보 낮춰 최대 2회 재시도(D11) 후 `PATCH_FAILED`, 시도 이력 전부 노출 | §6.4, §4.2 |
| LLM 비결정성 / 환경 차이 | 성공률을 확률적 지표로 정직하게 제시. 러너 버전 핀·아키텍처 고정으로 재현성 확보 | R2 |

> 재시도 상한은 **2회로 확정**되었다(방향 전환 D11 = PRD §6.4). 이전 문서의 "3회" 표기 불일치는 해소됨.

## 5. 신뢰도를 더 높일 수 있는 제안 (아직 미설계)

현재 PRD·코드에는 없지만, 넣으면 신뢰도가 크게 오르는 항목.

| 제안 | 효과 | 비고 |
|---|---|---|
| 재현성/멱등성 노출 | "같은 입력에 같은 결과"를 지표로 표시. 러너 버전 핀 + `--platform linux/amd64` 고정이 토대 | R2와 연결 |
| 신뢰도 점수(Confidence Score) | Finding마다 확신도 수치화. 안전 버전이 확정적인 CVE(높음) vs 영향 범위가 모호한 CVE(중간) | 신규 |
| 자기 자신에 적용(Dogfooding) | 우리 리포에 VibeGuard를 돌려 PR 생성 → "우리도 우리 도구를 믿는다"는 가장 강력한 증거 | PRD §14에 언급 |
| 제3자 검증 가능성 | PR의 회귀 테스트를 누구나 재실행 가능 → 우리 말이 아니라 기계가 증명 | 신규 |
| 버전·프롬프트 관리 투명화 | 어떤 프롬프트/Trivy/pytest 버전으로 검사했는지 리포트에 기록 | R2와 연결 |

## 6. 기본 / 검증 등급 신뢰도 관점 매핑

방향 전환의 언어 지원 등급(PRD §4.3)과 [BusinessModel](./VibeGuard_BusinessModel.md)의 FREE/PRO에 대응한다.

| 신뢰 축 | 기본 등급 (FREE, 모든 언어) | 검증 등급 (PRO, 테스트 있는 Python) |
|---|---|---|
| 검증 신뢰 | 제한적 (탐지 + 버전 상향 PR, **회귀 증명 없음**) | **전체 (설치→회귀 테스트 패치 전후 증명 + 게이트)** |
| 시스템 신뢰 | 동일 적용 (역할별 격리·적대적 검증·토큰 암호화) | 동일 적용 |
| 투명성 신뢰 | 기본 근거·Diff | **상세 리포트 + 감사 로그 + 실시간 스트림 + outcome 구분** |
| 정직성 신뢰 | "증명 없음(NO_TESTS)" 명시 | **실패 원인 구분(INSTALL_FAILED 등) + 시도 이력 전체 노출** |

> 검증 등급의 과금 가치가 곧 "회귀 증명 + 투명성 + 정직성 신뢰의 강화"임을 이 표가 보여준다.
