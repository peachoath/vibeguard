# VibeGuard 신뢰도 모델 (Trust Model)

> "AI가 고친 코드를 왜 믿을 수 있는가"를 정의하는 문서.
> VibeGuard의 신뢰도는 **검증 · 시스템 · 투명성 · 정직성** 4개 축에서 나온다.
> 대부분 [PRD](./VibeGuard_PRD.md)에 이미 설계되어 있으며, 이 문서는 그것을 "신뢰도" 관점으로 재배치한다.

## 0. 요약

VibeGuard의 신뢰도는 세 가지 질문에 답하는 데서 나온다.

1. **AI가 고친 결과를 믿을 수 있는가?** → 검증 신뢰
2. **우리 시스템 자체가 안전한가?** → 시스템 신뢰
3. **판단 근거를 투명하게 보여주는가?** → 투명성 신뢰

여기에 **"안 되는 건 안 된다고 말한다"**는 정직성 신뢰를 더한 4개 축이다.
심사에서 가장 임팩트가 큰 것은 단연 **검증 신뢰(TDD FAIL→PASS)** 이다.

```
             VibeGuard Trust
                    │
   ┌────────┬───────┴───────┬─────────┐
   ↓        ↓               ↓         ↓
 검증      시스템          투명성      정직성
 (증명)   (격리·최소권한)  (감사·근거) (실패 노출)
```

## 1. 검증 신뢰 — "고쳤다"가 아니라 "고쳐졌음을 증명"

VibeGuard의 심장이자 최대 차별점. (PRD §1.3, §6.4)

| 요소 | 설명 | 근거 |
|---|---|---|
| TDD FAIL→PASS 증명 | 패치 전 재현 테스트가 반드시 FAIL → 패치 후 PASS 확인. "진짜 취약했고, 진짜 고쳐졌다"의 기계적 증거 | PRD §6.4 |
| 오탐 게이트 | 패치 전 테스트가 이미 PASS면 "애초에 취약하지 않음"으로 분류하고 패치하지 않음 → 오탐 자동 차단 | PRD §6.4 Step 2 |
| Regression 게이트 | 기존 테스트 100% 통과해야만 PR 생성. 하나라도 깨지면 PR 차단 | PRD §6.4 Step 5, G4 |
| NVD/GHSA 교차 검증 | 스캐너 출력을 그대로 믿지 않고 공식 취약점 DB로 실제 위험도(CVSS)·영향 버전 재확인 | PRD §6.3 |
| 증거 첨부 PR | 재현 테스트 코드 + FAIL 로그 + PASS 로그 + 회귀 결과를 PR 본문에 첨부 → 사람이 눈으로 검증 | PRD §6.5 |

## 2. 시스템 신뢰 — "우리 도구 자체가 안전한가"

보안 도구가 보안이 허술하면 치명적. (PRD §11.1 NFR-S)

| 요소 | 설명 | 근거 |
|---|---|---|
| 샌드박스 격리 | 스캐너·테스트는 전부 Docker에서 `--network=none --read-only --cap-drop=ALL --memory=2g --pids-limit=256`로 실행 | NFR-S1 |
| 실행 타임아웃 | 컨테이너 300초 초과 시 강제 종료·부분 실패 처리 | NFR-S2 |
| 프롬프트 인젝션 방어 | 스캔 대상 리포의 README/주석을 **데이터로만** 취급, 지시문으로 실행하지 않음 + 툴 화이트리스트 이중 방어 | NFR-S6 |
| 최소 권한 | GitHub App 권한을 `contents:write` + `pull_requests:write`로 한정. main 직접 푸시·자동 머지 영구 금지 | PRD §6.5 |
| deny-by-default 훅 | Claude Agent SDK `PreToolUse` 훅으로 리포 밖 파일 쓰기, `rm -rf`, 외부 네트워크 호출 차단 | NFR-S5 |
| 토큰 암호화 | GitHub 토큰 AES-256-GCM 저장, 로그·SSE·에러 응답에 노출 금지 (`TokenCipher`로 구현됨) | NFR-S3 |
| 콜백 무결성 | Runner ↔ Spring Boot 콜백 HMAC-SHA256 서명 검증 | NFR-S4 |
| 데이터 최소 보관 | 클론 리포는 스캔 종료 후 즉시 삭제, 소스 영구 저장 금지(스니펫만 보관) | NFR-S8 |

---

## 3. 투명성 신뢰 — "왜 그렇게 판단했는지 보여준다"

블랙박스 AI는 신뢰받지 못한다. 판단 과정을 열어 보이는 것이 신뢰를 만든다.

| 요소 | 설명 | 근거 |
|---|---|---|
| 감사 로그 | 모든 에이전트 툴 호출을 `audit_logs`에 기록 → 사후 추적 가능 (PRO 차별 기능) | NFR-S7, §10 |
| 판단 근거(rationale) 노출 | Finding마다 CVE 정보·CVSS·판단 근거를 상세 탭에 표시 | F-06 |
| 실시간 진행 스트림(SSE) | 4개 에이전트가 무엇을 하는지 라이브로 노출 → "숨기지 않는다"는 인상 | F-04, §9.1 |
| Diff 뷰어 | 패치 전후 코드를 직접 비교(syntax highlight) | F-08 |
| TDD 증거 뷰 | FAIL 로그 / 테스트 코드 / PASS 로그 3단 표시 | F-07 |

## 4. 정직성 신뢰 — "안 되는 건 안 된다고 말한다"

과장하지 않는 것도 신뢰의 일부. (PRD §4.2, §15)

| 상황 | 시스템 동작 | 근거 |
|---|---|---|
| 증명 불가(패치 전 이미 PASS) | "정보성 Finding"으로만 표기, 패치하지 않음 | §4.2 |
| 패치 후에도 FAIL | 최대 N회 재시도 후 `PATCH_FAILED`, 시도 이력 전부 노출 | §4.2 |
| 회귀 테스트 깨짐 | PR 생성 차단, 깨진 테스트 목록과 함께 수동 검토 요청 | §4.2 `REGRESSION_BLOCKED` |
| LLM 비결정성 | 성공률을 확률적 지표로 정직하게 제시 | R2 |
| 재시도 무한 반복 방지 | 최대 N회 후 "Human Review Required"로 종료 | BusinessModel §4 ③ |

> 재시도 상한은 PRD §6.4(2회)와 사업모델 문서(3회)가 아직 불일치 — 구현 전 팀이 하나로 확정할 것.

## 5. 신뢰도를 더 높일 수 있는 제안 (아직 미설계)

현재 PRD·코드에는 없지만, 넣으면 신뢰도가 크게 오르는 항목.

| 제안 | 효과 | 비고 |
|---|---|---|
| 재현성/멱등성 노출 | "같은 입력에 같은 결과"를 지표로 표시 | NFR-P5(중복 PR 방지)는 이미 있음 |
| 신뢰도 점수(Confidence Score) | Finding마다 탐지 확신도를 수치화. SCA(버전 비교=높음) vs SAST(reachability 불확실=중간) 구분 | 신규 |
| 자기 자신에 적용(Dogfooding) | 우리 리포에 VibeGuard를 돌려 PR 생성 → "우리도 우리 도구를 믿는다"는 가장 강력한 증거 | PRD §14에 언급 |
| 제3자 검증 가능성 | PR의 테스트를 누구나 재실행 가능 → 우리 말이 아니라 기계가 증명 | 신규 |
| 버전·프롬프트 관리 투명화 | 어떤 프롬프트 버전/스캐너 버전으로 검사했는지 리포트에 기록 | R2와 연결 |

## 6. FREE / PRO 신뢰도 관점 매핑

| 신뢰 축 | FREE | PRO |
|---|---|---|
| 검증 신뢰 | 제한적 (탐지·패치만, TDD 없음) | **전체 (TDD FAIL→PASS + Regression + 재시도)** |
| 시스템 신뢰 | 동일 적용 (격리·토큰 암호화·최소 권한) | 동일 적용 |
| 투명성 신뢰 | 기본 근거·Diff | **상세 리포트 + 감사 로그 + 실시간 스트림** |
| 정직성 신뢰 | 검증 실패 시 "실패" 안내 | **실패 원인 분석 + 시도 이력 전체 노출** |

> PRO의 과금 가치가 곧 "검증·투명성·정직성 신뢰의 강화"임을 이 표가 보여준다.
